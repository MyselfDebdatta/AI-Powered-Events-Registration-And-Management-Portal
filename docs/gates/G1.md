## 3. Fresh-database bootstrap drill

Run against a freshly migrated database (zero users):

| Step | Request | Expected | Observed |
|---|---|---|---|
| 1 | `POST /api/auth/login` with any credentials | 401 | 401 |
| 2 | `POST /api/auth/bootstrap` with invalid token | 403 | 403 |
| 3 | `POST /api/auth/bootstrap` with valid `BOOTSTRAP_TOKEN`, email, password, name | 201, one admin, `must_change_password=true` | 201 |
| 4 | `POST /api/auth/bootstrap` again (valid token) | 409 | 409 |
| 5 | `POST /api/auth/login` with bootstrap credentials | 200, `must_change_password=true` | 200 |
| 6 | `POST /api/auth/change-password` with current + new password | 200 | 200 |
| 7 | `POST /api/auth/login` with new password | 200, `must_change_password=false` | 200 |

The advisory transaction lock (`pg_advisory_xact_lock(20261121)`) ensures two concurrent bootstrap requests cannot both create an admin. The second observes the first admin and fails with 409.

**No seeded credentials exist anywhere in the repo.** `db_init.py` no longer seeds; `config.py` has no `SEED_*` settings; `.env.example` files contain only unusable placeholders; `docker-compose.yml` requires all secrets from the environment.

## 4. Rate limiting

| Route | Limit | Mechanism | Blocked response |
|---|---|---|---|
| `POST /api/auth/login` | 5/min/IP + 20/hour/account | In-process sliding window (`app/core/rate_limit.py`) | 429 `RATE_LIMITED` + `Retry-After` |
| `POST /api/auth/bootstrap` | 3/min/IP | In-process sliding window | 429 `RATE_LIMITED` + `Retry-After` |

Choice recorded: in-process counts are sufficient for the single-replica S1 deployment. Cloudflare edge rules arrive in stage S3; a shared store is needed only when multiple replicas exist. Limits reset on process restart. Tests reset counters between cases so staff are never locked out.

**Direct-caller hardening (S1 remediation):** `client_ip()` uses `request.client.host` only. `X-Forwarded-For` is deliberately ignored: a direct caller can forge it and bypass the per-IP limit. Observed: 6 failed logins from one test client with 6 distinct `X-Forwarded-For` values returned `[401, 401, 401, 401, 401, 429]`; the 6th response carried `Retry-After` and code `RATE_LIMITED`. Trusting forwarded headers is deferred to stage S3, where the edge proxy set is known and can be validated. The 20/hour/account limit is unchanged.

## 5. Audit evidence

The following actions write `audit_log` rows (verified in the test suite with direct DB assertions):

- `LOGIN_SUCCEEDED`, `LOGIN_FAILED`
- `BOOTSTRAP_ADMIN_CREATED`, `BOOTSTRAP_FAILED`
- `PASSWORD_CHANGED`, `STAFF_CREATED`
- `PARTICIPANT_CREATED`, `PARTICIPANT_LIST_READ`, `PARTICIPANT_READ`, `PARTICIPANT_PHOTO_READ`, `LEGACY_QR_READ_REJECTED`
- `SESSION_CREATED`, `SESSION_LIST_READ`, `SESSION_READ`, `SESSION_UPDATED`, `SESSION_DELETED`
- `ATTENDANCE_RECORDED`, `ATTENDANCE_LIST_READ`, `ATTENDANCE_SESSION_READ`, `ATTENDANCE_STATS_READ`, `LEGACY_QR_REJECTED`, `FACE_MATCH_ATTEMPTED`
- `EMBEDDING_SYNC_READ_REJECTED`
- `ADMIN_DASHBOARD_READ`, `VOLUNTEER_LIST_READ`, `VOLUNTEER_CREATED`, `VOLUNTEER_STATUS_CHANGED`, `VOLUNTEER_DELETED`, `PARTICIPANTS_EXPORTED`, `ATTENDANCE_EXPORTED`

Every row carries actor id/role, action, entity/id, redacted before/after JSON, IP, user agent, request id and created_at. `email`, `phone`, passwords, tokens, photo keys and embeddings are redacted from audit JSON. Structured JSON logging applies the same redaction to application logs.

**Failure-path persistence (S1 remediation):** an audit row written on a path that then raises an `HTTPException` would otherwise be lost, because `get_db` rolls the request session back on the exception. Failure paths now write through `audit_log_detached()`, which commits in its own short-lived session. Observed after a wrong-password login and an invalid-token bootstrap against a live database: both `LOGIN_FAILED` and `BOOTSTRAP_FAILED` are queryable from `audit_log`. Deactivated-account failures also persist. Success paths still write through the request session, so no duplicate rows are created.

Sample query:

```sql
SELECT action, actor_role, request_id, created_at
FROM audit_log
ORDER BY created_at DESC
LIMIT 20;
```
